# 四周实施路线与交付边界

此路线依据已确认需求制定。原型已确认；按用户最新指示，已优先交付第 1 周的当前模型推理和第 2 周的真实数据主流程，见[本批验收](live-workflow-verification.md)。新闻数据连续覆盖、新闻模型与升级仍未完成。约四周后答辩，暂以 2026-11-21 左右作为时间窗，不把它写成用户给出的精确截止日。本期聚焦软件实现，不制作答辩材料。

## 原型阶段（本次交付）

- 五工作区暗色终端原型。
- 可操作的新建、演示训练、选模型、模拟控制与新闻对照场景。
- 清晰标注全部模拟数据，保持原生产代码和证据。
- 用户检查布局、联动和操作路径后，冻结交互规格。

## 第 1 周：验证高风险环节并确定真实数据路径

1. 将需求编号映射到数据结构、API 与状态转换；区分策略草稿、冻结版本、训练任务、模拟实例。
2. 验证冻结 PPO 对足够预热的当前闭合 1h K 线推理，不使用旧历史动作 CSV 代替模型。
3. 以保留测试区间外的有限新闻窗口做可访问性、覆盖、时间、实体/去重试验，测量下载量与本机资源。
4. 形成真实终端图表与实例选择的 API 契约；选择必要图表实现前先验证缩放、标记、许可证及离线部署方式。

出口：可确认的新闻数据方案、可重复的当前模型推理，以及已确认的界面原型。新闻覆盖不足时必须尽早说明具体缺口，不能把 C 偷换为新闻展示。

## 第 2 周：策略管理到当前模拟的完整流程

1. 可选 Binance 现货品种目录与 UI 数据下载任务，保留数据版本及质量状态。
2. 参数化规则/RL/预测配置，训练与回测任务可创建、查看、取消、重试。
3. 冻结模型包：权重、归一化、特征顺序、协议、数据与配置版本，避免新特征误用旧检查点。
4. 独立虚拟账户与实例生命周期；就绪握手、决策去重、暂停/恢复/停止与显式关闭模拟持仓。
5. 接入真实图表、信号、执行反馈、持仓和日志；旧恢复版保留可回退入口。

出口：用户独立完成规则和基础 RL 流程，至少两个实例隔离验证；任何盈利或成交数量不是工程完成的替代证明。

## 第 3 周：新闻训练因子与执行规则

1. 实现按决策截止时刻选择当时新闻版本与统一的小时聚合；明确迟到、修订、缺失与空事件。
2. 在预测模型和 RL 中接入统一新闻列；相同时间窗与费用下对照价格模型和新闻增强模型。
3. 当前推理采用与训练一致的输入语义；新闻源故障不得静默退化，风险门控与模型动作分别记录。
4. 新闻事件与策略决定可双向追溯，初期验证 BTC/ETH，其他币种显式显示能力范围。

出口：新闻确实被训练和当前模拟消费，开关比较可复查；不预设收益提升。

## 第 4 周：集成、异常恢复与使用验收

1. 验证模型切换 A/B、未平仓停止、重复操作、任务取消、进程重启、数据断流、部分下载和新闻缺失。
2. 核对多实例资金、订单与状态隔离，避免前端显示成功而引擎仍失败。
3. 完成终端交互、性能与本机资源检查，以测量结果决定并发上限。
4. 核心通过后实施有限候选/预算的研究比较与解释助手；不启用未经配置的 DeepSeek、不自动改代码或发布策略。
5. 用户按真实系统验收清单操作，保留每项证据、未通过项和回退版本。

出口：核心工作流可独立使用。低优先级增强若影响核心稳定性，列为明确未交付项，与用户确认后延期，不能标为完成。

## 迁移与工程约束

- 保留旧 SQLite、数据快照、模型、Git 历史与报告；先进行版本化兼容，不把旧证据改成新协议成果。
- 本次原型独立于现有 `apps/web`；用户确认后再把交互接入实际组件与 API。
- 复用 Freqtrade、现有 FastAPI/任务基础、SB3 和 LightGBM；仅在有明确缺口时引入新依赖，不同时替换多套引擎。
- 原有 Q4 保留数据不因新 UI 自动解禁为训练材料。新开发数据协议须明确各区间用途。
- 业务关键状态由服务端决定，localStorage 不承担生产模型、订单或资金真相。
- 免费公开数据与本机计算优先。后续 DeepSeek 配置由用户本机操作，旧聊天密钥不复用；本期不购买新闻数据或云资源。

这不是文件级实施步骤。界面反馈收敛后，再按确认规格拆分每阶段的代码任务、失败用例、验证命令和独立提交，避免在用户未认可布局时固化过细的实现。
